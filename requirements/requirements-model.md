# Модель требований (Задание 1, рисунок 1)

Требования лабораторной работы № 3 (US-1…US-10, UC-1…UC-11, ФТ-1…ФТ-12)
проанализированы и дополнены историями US-11…US-16 так, чтобы покрывалась
функциональность REST API: получение коллекций, управление корзиной,
регистрация/аутентификация, жизненный цикл JWT, webhook платёжного шлюза
и ведение справочников каталога.

**Формат:** Действующее лицо → User Story → Use Case.

| Актор | User Story | Use Case |
| --- | --- | --- |
| Гость, покупатель | US-1. Как покупатель, я хочу искать книги по названию, автору, тематике и издательству и просматривать карточку книги с отзывами, чтобы быстро найти подходящее издание. | UC-1 |
| Покупатель | US-2. Как покупатель, я хочу оформить заказ из корзины и оплатить его картой, чтобы получить книги без визита в магазин. | UC-2 |
| Гость | US-3. Как гость, я хочу оформить заказ, указав только контакт и адрес, чтобы купить конкретную книгу без затрат времени на регистрацию. | UC-3 |
| Покупатель | US-4. Как читатель профессиональной литературы, я хочу оформить предзаказ новинки и подписаться на новости издательства, чтобы гарантированно получить книгу сразу после поступления тиража. | UC-4 |
| Менеджер | US-5. Как менеджер, я хочу видеть список оплаченных заказов, проверять их и менять статусы, чтобы заказ был собран и доставлен без ошибок. | UC-8 |
| Покупатель | US-6. Как покупатель, я хочу добавлять книги в избранное, чтобы вернуться к ним позже. | UC-5 |
| Покупатель | US-7. Как покупатель, я хочу оставить отзыв и оценку купленной книги, чтобы помочь другим выбрать. | UC-6 |
| Покупатель | US-8. Как покупатель, я хочу отслеживать статус заказа, чтобы знать, когда придёт доставка. | UC-7 |
| Администратор | US-9. Как администратор, я хочу управлять каталогом (книги, авторы, тематики, издательства), чтобы ассортимент был актуален. | UC-9 |
| Покупатель | US-10. Как покупатель, я хочу получать уведомления о смене статуса заказа и поступлении новинок, чтобы вовремя реагировать. | UC-4, UC-7 |
| Клиентское приложение | US-11. Как клиентское приложение, я хочу получать коллекции ресурсов через REST API с пагинацией, фильтрацией и сортировкой, чтобы строить экраны каталога и заказов без избыточных запросов. | UC-13 |
| Покупатель | US-12. Как покупатель, я хочу управлять корзиной через API (добавить позицию, изменить количество, удалить), чтобы состав корзины сохранялся между сессиями и устройствами. | UC-12 |
| Покупатель, менеджер, администратор | US-13. Как пользователь, я хочу зарегистрироваться, войти в систему и получить JWT-токен, чтобы выполнять защищённые запросы к API. | UC-10, UC-11 |
| Покупатель, менеджер, администратор | US-14. Как пользователь, я хочу обновлять токен доступа и завершать сессию, чтобы доступ к API оставался безопасным после истечения срока действия токена. | UC-14 |
| Платёжный шлюз | US-15. Как платёжный шлюз, я хочу передавать результат оплаты через защищённый webhook, чтобы заказ переводился в статус «Оплачен» без опроса сервера клиентом. | UC-15 |
| Администратор | US-16. Как администратор, я хочу вести справочники авторов, издательств и тематик через API, чтобы данные каталога оставались согласованными. | UC-16 |

> Примечание о нумерации. В ЛР 3 таблица 4 использовала собственную нумерацию
> (UC-5 «Обработка заказа»), а детализированная диаграмма на рисунке 7 —
> расширенную (UC-5 «Управление избранным», UC-8 «Обработка заказа»).
> Здесь принята **единая нумерация рисунка 7 (UC-1…UC-11)**, к которой
> добавлены UC-12…UC-16.

Связь с функциональными требованиями ЛР 3: US-1 → ФТ-1, ФТ-2; US-2 → ФТ-4;
US-3 → ФТ-5; US-4 → ФТ-6, ФТ-7; US-5 → ФТ-8; US-6 → ФТ-3; US-7 → ФТ-9;
US-8 → ФТ-8, ФТ-11; US-9 → ФТ-10; US-10 → ФТ-11. Новые истории закрывают
требования, у которых в ЛР 3 не было отдельного варианта использования
(ФТ-3 — корзина, ФТ-10 — справочники), и добавляют API-специфичные сценарии.
